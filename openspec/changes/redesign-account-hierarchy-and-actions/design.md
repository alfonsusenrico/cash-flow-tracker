# Design

## Context

See [proposal.md](proposal.md) for the user-visible problem. `/accounts` currently has separate desktop and mobile account markup, and the desktop uses a multi-column layout with nested pocket cards. The same page already owns expansion state, account and sibling-pocket drag handlers, account mutation callbacks, transfer/trade/valuation/reconciliation dialogs, and the existing reorder endpoint. The screenshot with many Stockbit pockets is the discriminating fixture: spacing-only patches have not made that view coherent. This change replaces the layout model, not the finance model.

## Goals / Non-Goals

**Goals:** Keep one clear parent-to-child reading order, reveal supported actions in plain Indonesian, provide operable ordering without requiring drag, and keep many-pocket accounts compact without changing card height.

**Non-goals:** Change balances, valuation formulas, transfer/trade/reconciliation payloads, account API schemas, database schema, or unrelated forms. Do not introduce a new UI dependency or a different visual identity.

## Decisions

1. **Equal-height account cards.** Render top-level accounts in API order in a responsive grid: three columns at the wide-desktop (`2xl`) breakpoint, two at medium desktop (`xl`), and one below that. Every card has the same bounded height whether it contains pockets or not. The account summary and actions stay outside a flexible-height pocket viewport. Expanded children remain compact, border-separated rows; only that viewport scrolls when the list exceeds its available height. The page still scrolls between cards. Provide a visible pocket count, keyboard-reachable viewport, clear scroll affordance, and no horizontal clipping. Collapsing a pocket list preserves card height and ordering. Do not restore nested pocket mini-cards; verify that three columns do not crowd actions or values at the breakpoint.
2. **Shared action vocabulary, responsive placement.** Build the account/pocket action presentation from the existing handlers, with an accessible primary control and labelled `Opsi` disclosure for less frequent actions. Every top-level liquid account exposes `Tambah Kantong` as its primary `+` control whether or not it has pockets; an eligible source-specific `Pindah Saldo` action belongs in `Opsi`. An ordinary liquid pocket retains its direct transfer action. For an investment position, `Beli` and `Jual` remain prominent where applicable; valuation and housekeeping actions live in `Opsi`. An action disclosure is a real button/menu or inline disclosure with focus management, Escape/outside-dismissal if floating, and a restored focus target. Icon-only controls need accessible names; a toolbar full of small icon buttons was considered and rejected because it reproduces the reported confusion.
3. **Reuse existing operations and scope guards.** Keep the current account IDs, mutation hooks, confirmation dialogs, and transfer/trade/reconciliation flows. Derive available actions from the item's existing capabilities, not from whether it appears in the desktop or mobile tree. This prevents a mobile-only missing action. Preserve archive confirmations and mutation error feedback. Do not expose trade or valuation actions on unsupported account types.
4. **Ordering in one dimension.** Keep drag for pointer users, but add labelled move-up/move-down actions to top-level groups and sibling pocket rows. Calculate the new ID sequence from the current visible sibling group and call the existing `POST /api/accounts/reorder`. Disable unavailable edge moves, prevent pocket drags from starting a parent drag, and use the current query invalidation/error handling. This is preferable to changing the reorder API or asking keyboard/touch users to simulate dragging.
5. **Responsive information hierarchy.** Preserve the project's neutral structural surfaces, Spring Lime accent, configured account color, and tabular numerals. The header emphasizes name and balance; pocket rows prioritize name and amount, then type/symbol and investment cost/gain details only when applicable. At narrow widths, labels and values wrap into a deliberate stacked layout; actions remain at least 44×44 CSS pixels without obscuring amounts. Use fewer columns below each breakpoint when cards cannot fit without crowding controls; maintain row-major account order.
6. **Compact card actions and investment rows.** Put the supported primary action and `Opsi` in the upper-right of each card rather than below the balance. Use the same icon-only add-pocket control with an accessible name for top-level liquid accounts with zero or many pockets; keep source-specific transfer in `Opsi` when eligible. Investment positions retain short `Beli`/`Jual` labels where the transaction direction is consequential. Replace the large `Tutup kantong` button with a chevron beside the pocket count whose accessible name states whether it shows or hides pockets. In investment pocket rows, separate identity/instrument metadata from the valuation/gain group and keep trade/option controls in a predictable top-right cluster. The fixed card height and independently scrollable pocket area remain.
7. **One Settings destination per viewport.** Remove the top-bar gear. Desktop users keep the sidebar Settings control. On mobile/tablet, a top-bar menu button opens the existing navigation drawer, which contains the Settings control; this replaces the older mobile-header gear requirement without removing mobile access. Give icon-only controls accessible names, focus treatment, and approximately 44px hit areas.

## Risks / Trade-offs

- Nested pocket scrolling can hide rows or intercept page scroll → Keep the summary fixed, label the pocket region, allow keyboard and touch scrolling, expose the total count, and verify first and last rows plus actions in the twelve-pocket case.
- Consolidating actions could accidentally omit a desktop- or mobile-only flow → Inventory current actions by item type before implementation and test each reachable path at both breakpoints.
- Drag events and action clicks could interfere → Limit dragging to a clear handle or guard interactive descendants, and test reorder separately from disclosure activation.
- Dense investment metadata may overflow on small screens → Establish a consistent responsive row hierarchy and check long names, currency values, 320/390px widths, and 200% zoom in a browser.
- Floating option menus can mis-handle focus or clipping → Prefer a simple disclosure where practical; otherwise test focus return, Escape, outside click, and viewport placement.
- Dense real-world investment names, units, prices, and gains can exceed synthetic-fixture row heights → Test mixed stock, mutual-fund, and gold pockets with long names and values in 448px cards; verify no overlapping text or controls in both themes.
- Removing the header Settings shortcut can strand mobile users because the drawer trigger is currently unwired → Wire and verify the menu trigger before removing the gear; preserve Settings in the mobile drawer.

## Migration Plan

No data or API migration is required. Replace the current Accounts-page layout on a topic branch, run focused tests and browser checks against local data/fixture, and deploy through the normal release pipeline only after owner acceptance. A rollback is a code revert; persisted account order and financial records remain compatible.
