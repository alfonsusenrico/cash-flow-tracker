# Design

## Context
The worktree starts at mobile main 51d852e (2.2.0, code 21, Room v7). The backend contract is cash-flow-tracker 3310e24 (`text-capture` spec with History-Based Capture Suggestions, `routers/capture.py`, `services/text_capture.py`, `services/capture_suggestions.py`, `routers/transactions.py`). origin/main moved to 02f4468 during the work; the capture router, suggestions and resolution are unchanged there, and `text_capture.py` only adds plan linking after a write. The prototype `option-final.html` gives the capture screens and copy.

## Goals / Non-Goals
Goals: the Catat sheet with every state, a durable and idempotent capture queue, answers, undo, edit, delete from the tracker, and captures in Aktivitas and the home figures. Non-goals: backend changes, answering capture questions in Tanya, deleting captured moves from the phone, notification parsing.

## Decisions
1. **A separate `text_captures` table (Room 8).** One row per typed capture: client capture id (unique), text, device time, created time, local state, server id, the pairing that recorded it, the open question, the last capture view, transaction id, `undo_until` and its local deadline, a pending answer with its reply id, attempts, claim time, error code and an edited flag. The 7→8 migration creates only this table and its two indices, using the exported schema's SQL. Rejected: storing captures in `raw_notifications`, which would mix typed text into every notification query, filter and retention rule.
2. **Local state machine.** `queued → sending → recorded | needs_detail | undone | failed`, plus `deleted` after "Hapus dari tracker". `queued` keeps the reason (`network`, `server`, `auth`, `not_paired`). Server statuses map one to one. A refusal (4xx other than 401/403/429) is `failed` and is resent only by the owner. Rejected: retrying 422 automatically, which would loop on text the tracker will never accept.
3. **Write first, then send; one sender at a time.** A capture is inserted before any request. A send claims the row with one conditional UPDATE (`queued`, or `sending` older than 90 s, which is longer than connect plus read timeouts). The process start returns every `sending` row to `queued` because no send can be running yet. Every send carries the stored `client_capture_id`, so a resend after a lost response returns the same capture. Rejected: a resend keyed by row id, which the tracker cannot deduplicate.
4. **Resend under the auto-sync switch.** The first send happens at once when the owner taps "Proses dengan AI". A transient failure schedules a unique WorkManager job with a network constraint only when auto-sync is on. "Kirim", "Coba lagi" and "Sinkron sekarang" are owner actions and schedule it regardless. Turning auto-sync off cancels it; turning it on enqueues it. Rejected: resending from DirectSync, which is for notifications and runs on capture events.
5. **Undo window on the phone's clock.** The first recorded view fixes `undo_deadline = now + clamp(undo_until − Date header, 0, 10 s)`, so a resend that finds an old capture does not reopen the window. "Batalkan" is shown and sent only before the local deadline (9.9 s sends, 10.1 s does not); the server's 5 s grace absorbs transit. A 409 closes the window locally. An edit ends it. Rejected: comparing `undo_until` with the phone's clock directly, which a skewed clock would break.
6. **Answers are stored with their reply id.** The same answer reuses the stored reply id on every resend; a different answer gets a new one. Answers are checked against the open question before storing (option offered, typed amount within 50 characters, or an owner-picked UUID when "other" is allowed). 422 and 409 clear the stored answer; 409 then reloads the capture. Network and server failures keep it for "Kirim ulang jawaban".
7. **"Hapus dari tracker" only for the capture's own expense or income.** Offered when the capture is recorded under the current pairing and the tracker's view shows an expense or income whose id is the capture's transaction. 200 and 404 both mark the capture deleted, with 404 reported as already gone. A captured move is not offered, because `DELETE /api/transactions/{id}` refuses movement legs and the movement endpoint is not part of the approved scope.
8. **The sheet is an overlay, not a dialog window.** The shell hides the tab from TalkBack while the sheet is open, back and the close button close it, and only the scrim above the sheet closes on a tap. The sheet uses a shaped background, not a clip, so its content stays touchable everywhere. Rejected: a Compose `Dialog`, whose window and clip interfered with touch delivery in the JVM test environment.
9. **Processing shows the tracker's steps without fake progress.** The phone cannot see the server's progress, so the three prototype steps are listed together under "AI memproses…" with a skeleton; the shimmer is removed when animations are off. Rejected: timed step ticks, which would invent progress.
10. **Suggestions are history only.** Loaded when the sheet opens on a new capture; invalid items are dropped; empty hides the section; a failed load says so. A tap fills and focuses the input and never sends. The prototype's placeholder "bayar parkir ptc 10rb" remains as an input hint, not as a suggestion.
11. **Where captures appear.** Aktivitas merges captures and notifications by time with "Diketik di ponsel" (the web's `capture` source label); Semua lists all live captures, Perlu cek the unrecorded, Di ponsel those the tracker has not accepted. Captures with a question open their sheet. Home figures add recorded captures, with moves under "Pindah", and count waiting captures as "catatan". The tracker's summary is fetched again after a capture changes the ledger and is never mixed with local figures.
12. **The existing edit form serves both.** `TransactionForm` takes a `FormSeed` (key, amount, type, notes) built from a notification or a capture, so "Ubah" uses the same fields, checks and PATCH.
13. **Spec deltas.** `companion-interface` is modified too, because its home-figures requirement named only notifications; every scenario name is kept and one is added.

## Data, API and failure behaviour
- `POST /api/capture/text` `{client_capture_id, text, device_time}` with an ISO offset and seconds; the `+` is percent-encoded by the client. 200 is valid only when its id is a UUID, its client id matches and a needs-detail view carries an answerable question. 401/403 → queued `auth`; 429/5xx/invalid 200 → queued `server`; I/O → queued `network`; other 4xx → failed with `detail.code`.
- `POST /api/capture/{id}/answer`, `/undo`, `GET /api/capture/{id}`, `GET /api/capture/suggestions?device_time=…`, `PATCH` and `DELETE /api/transactions/{id}` use the same Bearer key and loopback test transport. Logs contain no capture text or amounts.

## Migration and rollback
7→8 adds `text_captures` only; the migration test compares every pre-existing table and index definition before and after and keeps rows of all three tables. Rolling back to 2.2.0 would meet a version-8 database without a downgrade path, so the rollback for an installed 2.3.0 is a reinstall of 2.2.0 after clearing app data, which loses local rows; keep 2.3.0 installed instead and fix forward. The upgrade check on the verification app is `CaptureUpgradeDeviceTest`.

## Risks / Trade-offs
- The JVM UI tests do not prove touch delivery on a phone; `CaptureBackendDeviceTest` does, and it needs the Realme.
- A capture whose first attempt timed out cannot be discarded locally, because the tracker may have recorded it; a resend settles it.
- Undone and deleted captures stay in Room, hidden; they are small and keep the idempotency record.

## Open decisions for owner
1. **Deleting captured moves from the phone.** Conservative choice: not offered; the page points to Tracker Web. The alternative is `DELETE /api/movements/{id}` from Rincian.
2. **Capture questions in Tanya.** Conservative choice: answered in the capture sheet, reopened from Aktivitas or Rincian; the Tanya count stays notification-only. The alternative is listing them in Tanya.
3. **"Catat manual" in the prototype's error state.** Not offered, because the phone has no create-transaction path; the error offers "Coba lagi" and "Tutup".
4. **Input placeholder.** Kept as the prototype's "bayar parkir ptc 10rb". It is a hint inside the empty field, never a tappable example.
